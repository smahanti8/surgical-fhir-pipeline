The problem this solves

Surgical robotics platforms generate rich telemetry — procedure events, device inventory, physiologic streams. Almost none of it is exchangeable as emitted. It arrives shaped for engineering: high-frequency, denormalised, coded in a local vocabulary no receiving system has heard of.

Getting it into an EHR, a surgical registry, or a post-market surveillance system means crossing into FHIR. That crossing is where healthcare interoperability actually lives — and it is mostly not a technical problem. It is a semantics and governance problem.

Who this is for

This pipeline is built for the person asking:

  • Clinical Informaticists evaluating whether OR platform data can realistically reach a registry
  • Health IT Architects scoping a medtech interoperability engagement
  • Data Engineers who need to understand the governance layer, not just the JSON shape

What makes this different from a standard FHIR demo

🚫

Drop, don't degrade

An unmapped procedure code or missing laterality drops the case entirely. Emitting a text-only, uncoded procedure record is worse than absent — it's invisible to every meaningful query while still looking like data.

📋

Quality report as first-class output

The governance artefact is not documentation — it is a primary deliverable that enforces referential integrity. An early bug (orphan Procedures) was found only because the report counted resources by type.

⚖️

Every decision is arguable

The pipeline documents the counter-argument for every design choice. A registry might prefer text-coded records to none. This is not hidden — it is in DECISIONS.md.
