# Security

This document states the security posture of `surgical-fhir-pipeline`
plainly. See [`ARCHITECTURE.md §6`](ARCHITECTURE.md) for the full list of
explicit scope limitations this repo carries by design.

---

## Scope

This is a mapping and governance demonstrator over synthetic data — not a
system of record, not a FHIR server, and not deployed anywhere with real
patient data. The posture below describes what protects the demonstrator,
not what a production deployment would additionally need.

---

## Data handling

- **No real PHI, ever.** Every `SurgicalCase` in this repo is generated by
  `generator.py` from a fixed `seed`. There is no code path that ingests or
  stores real patient data, and none should be added — see
  [`.claude/rules/phi-handling.md`](.claude/rules/phi-handling.md).
- **`_pseudonymise` (`mapping.py`) is explicitly NOT de-identification.** It
  is a SHA-256 hash of the local MRN, truncated to 16 hex characters. A
  deterministic hash of a small identifier space is a pseudonym, not
  de-identified data — the same input always produces the same output, and
  the MRN space `generator.py` draws from is small enough that the mapping
  is reversible by brute force. This is only defensible here because the
  input is synthetic. A real deployment needs a separate de-identification
  process with its own key custody and audit trail; this repo does not
  implement one, and says so rather than implying otherwise.

## API security posture

`api.py` exposes six routes, all `GET`: `/metadata`, `/quality-report`,
`/governance-kpis`, `/Encounter/{id}/$everything`, `/{resource_type}/{id}`,
and `/{resource_type}` (search). There is no `POST`, `PUT`, `PATCH`, or
`DELETE` route anywhere in the file.

The only method on `FHIRStore` (`store.py`) that mutates state is `load()`.
It is loaded only during application construction (`create_app()` in
`api.py`) — once for the bulk mapped resources, and once more per case for
each generated `Provenance` resource — and never from a request handler.
By the time the app object is returned and can accept HTTP traffic, loading
is already finished. In other words: **nothing reachable over the API can
write.**

There is no authentication on any route. This is a deliberate scope
decision, not an oversight: with no write surface and no real data behind
it, there is nothing yet for an auth layer to protect. Adding SMART on FHIR
auth is listed as future work in `ARCHITECTURE.md §7` and is a prerequisite
for any deployment reachable outside a local machine, or that loads
anything other than synthetic data.

## Out of scope

The full list of explicit limitations — no persistence, no write API, no
validated terminology server, no FHIR validator in CI — lives in
[`ARCHITECTURE.md §6`](ARCHITECTURE.md) and is not repeated here.

## Reporting a concern

This is a synthetic-data demonstration repository with no production
deployment. If you find a security concern:

- For anything sensitive, use GitHub's private vulnerability reporting
  (repository **Security** tab → **Report a vulnerability**).
- Otherwise, open a public issue.
